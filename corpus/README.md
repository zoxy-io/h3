# Vendored corpus

RFC 9001 Appendix A's worked packets — a client Initial, a server Initial, a
Retry, and a ChaCha20-Poly1305 short header — checked octet for octet against
what this package produces.

It is a gate rather than a nicety, and the reason is specific. Every other test
of the protection path checks it *against itself*: a packet is sealed and then
opened, and the two agree. That catches a great deal and cannot, even in
principle, catch a **shared** misreading — a nonce built wrong in both
directions, associated data that omits the same octets twice, a header
protection mask sampled from the same wrong offset. Only bytes someone else
produced can catch those, and the appendix is those bytes.

The strongest single case is A.2: sealing the appendix's header and payload has
to reproduce its 1200-octet protected packet exactly, which requires the nonce,
the associated data, the AEAD, the sampling offset, the mask, and the choice of
which first-octet bits the mask applies to all to be right at once.

## The vectors are machine-lifted, not typed

Transcription is exactly where a codec's test vectors go wrong, and quietly: a
mistyped byte string still decodes to *something*, so the test fails against a
plausible answer and the reader blames the decoder.

So `rfc9001_vectors.zig` is generated by [`extract.py`](extract.py) from the RFC
text, and **every block is checked against a length the RFC states in prose**.
If an anchor ever matches the wrong block, the byte count disagrees and the
extractor fails instead of emitting a wrong fixture. That check earned itself
twice while it was being written: once on A.1's secrets, whose values wrap onto
a continuation line, and once on A.2's payload, where the appendix prints a
245-octet CRYPTO frame and states the remaining 917 octets of PADDING in prose
rather than showing them.

Regenerate with:

```sh
curl -sSL -o rfc9001.txt https://www.rfc-editor.org/rfc/rfc9001.txt
python3 corpus/extract.py rfc9001.txt > corpus/rfc9001_vectors.zig
```

`rfc9001.txt` is not vendored: it is 123 KiB of prose, the extractor names the
document it expects, and the length checks make a wrong or truncated download
loud rather than silent.

## One thing the appendix does not claim

A.3's ACK frame acknowledges packet number **0**, not the 2 that A.2's client
Initial carries. The two examples are not a matched exchange — A.3 says only
"the server sends the following payload in response" — so the corpus asserts
what the appendix has rather than what a coherent exchange would have. Noted
here because the first instinct on seeing 0 is that the decoder is wrong.

## What is not here yet

Encodings captured from other implementations, the way
[zoxy-io/hpack](https://github.com/zoxy-io/hpack) vendors
http2jp/hpack-test-case. RFC 9001's appendix proves agreement with the
specification; it does not prove agreement with the implementations a real peer
is running, and a stack can satisfy the first and still mishandle something the
RFC never demonstrates. That wants a second corpus and is tracked with the
connection slice.
